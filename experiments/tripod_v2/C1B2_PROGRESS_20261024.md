## 1. 当前结果与正确的Gate标记

- **C1-B2 Native Y plane (2560×1440→320×180)**：Host PASS。输入是直接从本机FFmpeg/OpenCV源视频解码出来的yuv420p亮度平面，不经过BGR。Native C++按照Camera声明的rowStride/pixelStride执行8×8面积缩小，输出是由调用者持有的独立320×180缓冲区。
- **C1-B2 Native特征预稳定**：Host PASS。20行真实Gyro/19个RS区间、39×65为特征网格密化，不是39个物理RS行；输入和原C1B使用相同qCenter。Native Valid Mask和参考实现完全一致；灰度最大差1级。
- **Host“真实Y Plane已经可用”→当前SourceID视觉结果33.78ms**：四段各291原RAW、290相邻视觉pair，合计1160/1160当帧执行PASS。严格异步worker按SourceID/TS检查，超时结果不会挪用下一帧。
- **更严格20ms纯视觉预算**：886/1160（76.4%）；仍有近四分之一帧超过20ms，需要更多余量给真实设备与最后的GPU/编码。
- **这不是Android实时PASS**：33.78ms起点是Host本地软件解码结束、原始Y平面送到算法时刻，不是真机Camera YUV_420_888回调时刻，也不包含最终高清GPU ONE-WARP、EGL、Encoder。Y1 Device fps/功耗/Stop-Flush：NOT_TESTED。

- **前缀因果性**：024630完整291帧与独立前80帧（用200msHost预算排除调度随机超时因素）的前79个Native观测数值逐帧完全一致；未读未来Camera帧/未来Gyro/离线Oracle。

## 2. 源头问题定位

旧C1-B Host通过 Windows MP4→BGR→灰度→缩小→RS19→Native LK；严格从BGR软件解码开始按33.78ms截止，四视频只有101/1160个视觉pair及时返回。但这不能证明设备Camera回调也会这么慢。

新C1-B2：FFmpeg/OpenCV用CAP_PROP_CONVERT_RGB=0，直接暴露原yuv420p解码的Y平面为2560×1440 uint8；Native处理Y平面并直接调用20物理行RS19特征预稳定，随后C++异步多区域LK。去掉BGR转换后，软件解码CPU时间也明显下降。

**重要技术限制**：Host FFmpeg/OpenCV曾警告“unsupported picture format yuv420p, treated as 8UC1”，我们实际校验其尺寸、亮度、缩小与原数据匹配；这只能当Host实验取Y的路径，不是可靠的Android生产API。设备端应使用AImage/Image.Plane/YUV_420_888正式接口并严格验证行/像素步长与生命周期。

## 4. 精度、内存安全和时间测试

1. Native独立单元：rowStride=2688、pixelStride=2、非Y字节哨兵251/255，输出完全相同、未触碰padding/UV；Native输出与源Y解码分离，不保留已回收Camera buffer的指针。
2. 随机uint8 Y 2560×1440面积缩小：Native与OpenCV INTER_AREA最大差1灰度级；原视频真实Y plane下同样最大差1。
3. 20个物理RS Gyro行＋39×65特征网格：Native预稳定与先前cv2.remap validMask bitexact、有效像素最大差1灰度级。它不是最终高清Warp精度证明。
4. 原SourceID 4～294、PTS、SensorTS全程逐帧核对，每个真实Gyro查询落在Camera冻结读出截止点；明确+8ms冻结偏移；未添加未来帧或Oracle。
5. 024630独立前80帧及完整291帧的前79个Native数值输出精确一致（超时时限差别不影响数据），说明没有用未来视频数据改变当前决策。
6. 先前C1B Host Busy/Backpressure、乱序、超时、取消、Stop/Join和旧SourceID禁止复用测试保持PASS；本次四段实流1160/1160视觉按当前SourceID返回。
